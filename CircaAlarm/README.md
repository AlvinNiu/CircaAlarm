

# 生物钟闹钟iOS应用需求文档

## 1. 产品概述

### 1.1 产品定位

#### 1.1.1 核心概念：基于睡眠周期理论的智能唤醒系统

生物钟闹钟是一款专为iOS平台设计的智能睡眠辅助应用，其核心理念建立在经过广泛验证的睡眠周期理论基础之上。现代睡眠科学研究表明，人类睡眠并非均匀连续的状态，而是由多个约**90分钟（即1.5小时）**的周期组成，每个周期包含浅睡眠（N1、N2阶段）、深睡眠（N3阶段）和快速眼动睡眠（REM阶段）的完整 progression。在深睡眠阶段被强制唤醒会导致显著的**睡眠惯性**（sleep inertia）——表现为定向障碍、认知功能下降和持续30分钟至数小时的昏沉感。相反，在浅睡眠阶段自然或温和唤醒，用户能够迅速进入清醒状态，保持更好的日间警觉性和情绪稳定性。

本应用采用**纯时间模型驱动**的设计范式，区别于市场上依赖传感器监测的智能闹钟（如Sleep Cycle、Pillow等）。这类竞品通常利用手机加速度计或麦克风实时检测睡眠阶段，并在此基础上动态选择唤醒时机。然而，传感器方案存在固有局限：需要特定设备摆放位置、受环境干扰影响准确性、持续后台运行增加功耗、以及潜在的隐私敏感问题。本应用完全摒弃传感器依赖，转而基于用户主动输入的时间数据和经过科学验证的睡眠周期参数进行预测性计算，以**极简架构**实现**可靠优化**。

纯时间模型的技术路径带来三重核心优势：**隐私零风险**（无音频或运动数据采集）、**电池高效率**（无需持续传感器运行）、**使用零负担**（无需特定设备位置）。用户只需在睡前进行一次点击操作，后续所有计算均在本地完成，闹钟触发通过iOS系统级本地通知机制实现。这种设计选择是对"智能"概念的重新诠释——从**实时检测**转向**科学规划**，从**算法黑盒**转向**用户可控**，从**功能堆砌**转向**体验聚焦**。

#### 1.1.2 目标用户：追求高质量睡眠体验的iOS用户

本应用的目标用户群体具有清晰的画像特征和行为模式。核心用户为**25-45岁的都市职场人群**，处于职业发展关键期，面临工作压力大、作息不规律、对日间精力管理有切身需求的现状。这一群体普遍具备中等以上数字素养，熟悉iOS生态系统，愿意为提升生活品质的工具付费，同时对隐私保护有较高敏感度。次级用户包括**学生群体**（面临学业周期和不规律作息挑战）和**自由职业者**（需要自我管理作息节奏）。

| 用户维度 | 特征描述 | 核心需求 |
|:---|:---|:---|
| 人口统计 | 25-45岁，中等以上收入，iPhone主力用户 | 简洁可靠的工具，无学习成本 |
| 心理特征 | 健康意识强，自我提升动机明确，数据驱动思维 | 科学有效的睡眠优化方案 |
| 技术态度 | 重视隐私，对传感器监测持谨慎态度 | 本地运行，数据自主可控 |
| 使用场景 | 晚间睡前标记、清晨闹钟交互、日间数据回顾 | 无缝融入现有作息流程 |
| 痛点现状 | 传统闹钟唤醒痛苦，传感器应用复杂不可靠 | 温和唤醒，简单可信 |

用户的典型使用旅程呈现明显的时段特征。**晚间睡前（21:00-24:00）**是核心交互时段——用户完成睡前准备后打开应用，查看次日闹钟安排，点击"我要睡了"按钮标记睡眠意图，可能快速调整当晚的入睡时间预期。**清晨（依个人设定，通常6:00-9:00）**是第二个关键触点——闹钟在计算的浅睡眠窗口内温和响起，用户选择停止或延迟，并在清醒后标记舒适度反馈。**日间时段**用户可能查看历史记录和统计数据，评估近期睡眠趋势，调整设置参数以优化后续体验。

从竞品使用经验来看，目标用户往往已经尝试过多种睡眠工具：传统闹钟过于简单粗暴，经常导致痛苦的起床体验；传感器驱动的睡眠周期应用存在准确性疑虑，对设备放置和佩戴方式有要求；可穿戴设备虽然数据丰富，但睡眠期间佩戴可能带来不适感，且设备成本较高。本应用的纯时间模型设计正是针对这些痛点，提供一个**无需额外硬件、操作极简、理论依据明确**的替代方案，吸引那些认可睡眠周期科学、追求简洁有效工具、重视隐私保护的用户群体。

#### 1.1.3 差异化特点：纯时间模型驱动，无需传感器监测

本应用在市场竞争格局中占据独特的生态位，核心差异化优势集中体现在技术架构的根本性创新上。

| 对比维度 | 传统闹钟 | 传感器驱动应用（如Sleep Cycle） | 本应用（纯时间模型） |
|:---|:---|:---|:---|
| 唤醒策略 | 固定时间，无视睡眠阶段 | 实时检测，动态选择时机 | 科学计算，预测性规划 |
| 硬件依赖 | 无 | 手机传感器或可穿戴设备 | 无 |
| 使用准备 | 即开即用 | 需特定摆放位置或佩戴 | 即开即用 |
| 隐私风险 | 无 | 持续音频/运动数据采集 | **零传感器权限** |
| 电池影响 | 可忽略 | 显著耗电（后台持续运行） | **极低耗电** |
| 准确性基础 | 无 | 传感器数据+机器学习推断 | 用户输入+科学理论模型 |
| 用户控制感 | 完全可控 | 算法黑盒，被动接受 | **透明计算，主动参与** |
| 核心局限 | 无视生理节律 | 检测误差，环境干扰 | 个体差异，理论简化 |

纯时间模型的设计哲学强调**"辅助而非替代"**——应用不声称诊断或治疗睡眠障碍，而是作为智能工具在现有作息框架内实现更优唤醒效果。这种定位既是对技术能力的诚实界定，也是对用户自主性的尊重。用户通过"我要睡了"按钮主动宣告意图，通过调整参数反映个体特点，通过舒适度反馈参与系统优化——这种**"人机协同"**模式比全自动算法更能建立长期信任关系。

从长期演进角度，纯时间模型架构保留了灵活的扩展空间。未来版本可考虑基于用户长期舒适度反馈数据，**推断个性化最优周期时长**（如从默认90分钟调整为85或95分钟）；或引入可选的Apple Watch心率数据集成，在保持本地处理的前提下增强唤醒时机精度。但这些增强功能始终作为**可选附加项**，核心体验保持简洁和零依赖。

### 1.2 核心价值主张

#### 1.2.1 在浅睡眠阶段唤醒，减少起床不适感

本应用的首要价值承诺是**显著改善晨起体验**，其核心机制在于利用睡眠周期理论优化唤醒时机。睡眠医学研究一致表明，唤醒时机对晨起后的主观感受和日间功能表现具有决定性影响。当闹钟在深睡眠阶段响起时，大脑需要经历从高度同步的慢波活动状态到清醒状态的剧烈转换，这一过程伴随着认知功能的暂时性损害和情绪状态的负面波动。相比之下，在浅睡眠阶段（特别是周期末段的N2浅睡眠或REM睡眠）唤醒，大脑活动已经呈现出去同步化特征，接近清醒状态的生理模式，外部唤醒信号的"侵入性"显著降低。

应用实现这一价值的技术路径是**精确计算并瞄准"预设起床时间前的最后一个完整睡眠周期结束点"**。具体计算流程如下：

| 步骤 | 操作 | 示例（预设7:00起床） |
|:---|:---|:---|
| 1 | 记录"我要睡了"点击时间 | 23:30 |
| 2 | 加入睡所需时间（默认10分钟） | 估算入睡时间 = 23:40 |
| 3 | 计算到目标时间的可用时长 | 7小时20分钟 = 440分钟 |
| 4 | 计算完整周期数（向下取整） | 440 ÷ 90 = **4个完整周期** |
| 5 | 计算最佳唤醒时间 | 23:40 + 6小时 = **5:40** |
| 6 | 应用唤醒窗口（默认±10分钟） | 实际响铃窗口：5:30-5:50 |

这一计算结果表明，用户将在**5:40左右**（第4个完整周期结束点，浅睡眠阶段）被唤醒，比预设起床时间**提前80分钟**。这种"睡眠损失"是为了换取在浅睡眠阶段唤醒的舒适度提升——用户避免了在6:10-7:00期间可能进入的第5个周期中段被深睡眠唤醒的痛苦体验。

需要坦诚说明的是，这一策略涉及**明确的权衡取舍**：牺牲部分睡眠时间以优化唤醒质量。对于睡眠时长敏感的用户，系统提供了**兜底策略**作为平衡——可以设置最晚响铃时间（如7:15），或选择严格在预设时间响铃。应用的设计哲学是**优先保证周期完整性**，但尊重用户的最终决策权。

唤醒体验的优化还通过**渐进式响铃设计**进一步强化：音量从低水平逐步提升，配合柔和的铃声选择（自然音效或轻音乐），模拟自然醒来的过程。这种多感官的温和过渡，相比传统闹钟的突然大声刺激，显著降低了晨起应激反应。

#### 1.2.2 完全本地运行，保护用户隐私

在当代数字健康应用领域，**数据隐私已成为用户决策的核心考量因素**。本应用将"完全本地运行"作为基石性设计原则，从根本上回应这一关切，形成显著的差异化竞争优势和市场信任基础。

"完全本地运行"的技术内涵是：应用的所有功能——包括睡眠记录存储、统计分析、闹钟触发逻辑——均在用户设备上独立完成，**不涉及任何数据向远程服务器的传输**。这一架构的具体实现涉及两个层面：

| 数据层级 | 存储机制 | 具体内容 | 技术细节 |
|:---|:---|:---|:---|
| 轻量设置层 | **UserDefaults** | 用户偏好设置（起床时间、入睡延迟、铃声选择等） | JSON编码，键值存储 |
| 大量记录层 | **SQLite数据库** | 睡眠历史记录（时间戳、行为数据、舒适度反馈等） | 关系型表结构，本地文件 |

用户数据以加密格式存储在应用沙盒内，仅对应用自身可访问，iOS系统的安全架构提供基础保障。更重要的是，**数据生命周期完全封闭在设备边界内**：生成、处理、存储、分析、展示，无任何环节涉及网络通信。即使用户启用iCloud设备备份，数据也仅以加密形式存在于用户的个人iCloud账户中，应用开发者无法访问。

从隐私风险角度，完全本地运行消除了多重敞口：**传输截获风险**（无网络通信）、**服务端泄露风险**（无集中存储）、**第三方共享风险**（无数据合作）。这种"气隙"式架构为用户提供了最高级别的隐私保障。对于企业环境或高度敏感用户，未来版本可考虑集成**SQLCipher数据库加密**，在设备丢失或被盗场景下提供额外保护。

完全本地运行的设计也带来了功能层面的取舍：无法实现跨设备实时同步、无法基于聚合数据进行群体研究、无法提供需要云端算力的复杂分析。然而，对于目标用户群体，这些取舍是可接受的——他们更看重**隐私确定性**而非功能丰富度，更愿意为**数据主权**放弃便利性。应用通过精心设计的本地分析功能和标准格式数据导出（CSV/JSON），在纯本地架构内最大化用户价值，同时支持用户随时迁移或备份自己的数据资产。

#### 1.2.3 数据驱动持续优化个人作息

本应用的长期价值在于将睡眠数据转化为**可行动的洞察**，支持用户建立更健康的作息习惯。这一价值超越了单次闹钟功能的优化，指向更深层的睡眠健康管理目标，为应用建立了持续的用户粘性和成长空间。

数据驱动优化的基础是**全面、准确、长期的数据记录**。应用捕获的睡眠数据维度包括：

| 数据类别 | 具体字段 | 用途说明 |
|:---|:---|:---|
| **时间数据** | 点击时间、估算入睡时间、计划/实际唤醒时间 | 周期计算准确性评估，作息规律性分析 |
| **行为数据** | 延迟次数、使用的唤醒策略 | 起床困难程度识别，策略有效性对比 |
| **反馈数据** | 舒适度标记（舒适/不舒服/跳过） | 唤醒质量主观评估，个性化优化依据 |

这些多维度数据经过聚合分析，转化为用户可理解的趋势和指标。**核心统计维度**包括：睡眠时长趋势（7/30/90天滑动平均）、入睡时间分布热力图（识别作息规律性）、醒来舒适度比例（评估策略有效性）、延迟使用频率（反映起床困难程度）。这些结果以图表形式可视化呈现，帮助用户直观把握自身睡眠状况的变化模式。

**健康评估层**基于统计数据生成个性化建议。系统内置参考标准（成人推荐睡眠时长7-9小时、作息规律性指标），将用户数据与标准对比，识别偏差和改进空间。建议生成采用规则引擎方法：连续多日睡眠时长<6小时触发"睡眠不足"警告，入睡时间标准差>60分钟提示"作息不规律"，延迟使用频率>50%建议"调整起床时间"。建议的呈现注重**可操作性和温和性**——避免制造焦虑，提供具体、渐进式的调整方案。

长期优化机制强调**用户参与和反馈闭环**。用户可以对系统建议进行反馈（"有帮助"/"无帮助"/"已尝试"），这些反馈用于优化建议算法的个性化程度。随着数据积累，应用可以识别用户的**"最佳睡眠窗口"**——历史上舒适度评分较高的睡眠时段特征，并将这些洞察融入后续建议生成。这种"学习-建议-反馈-优化"的循环，使得应用价值随使用时间增长而提升，形成强大的用户留存动力。

## 2. 核心功能模块

### 2.1 睡眠周期智能计算引擎

#### 2.1.1 入睡时间估算机制

##### 2.1.1.1 "我要睡了"按钮触发时间点记录

"我要睡了"按钮是用户与应用交互的**核心入口**，其设计直接影响数据质量和使用体验。按钮位于应用主界面显著位置，采用**大尺寸圆形设计**（直径不小于屏幕宽度的40%），配以柔和的视觉风格——径向渐变背景从中心青蓝色（#5AC8FA）向边缘深紫色（#5856D6）过渡，模拟夜空的视觉效果，表面有 subtle 的脉动动画（周期4秒），暗示呼吸节奏引导放松。

按钮的交互设计经过精心优化：**按下时缩放至0.95并加深颜色**，释放后恢复并触发触觉反馈（`UIImpactFeedbackGenerator(style: .heavy)`），同时播放轻柔的确认音效。这种多感官反馈在半清醒状态下提供明确的操作确认。点击后应用切换至"睡前确认页"，而非直接完成记录——这一中间步骤允许用户发现误操作后返回，也为展示计算预览信息提供空间。

时间点记录的精度达到**毫秒级**，存储为完整的`Date`对象，包含时区信息以正确处理跨场景。记录同时触发本地通知的调度准备：如果用户后续完成确认流程，通知正式注册；如果取消或中断，通知撤销避免残留。从用户体验角度，点击操作标志着"睡眠意图"的正式表达，但应用明确传达这**不等于立即入睡**——后续界面显示"预计23:40入睡"等提示，管理用户预期并邀请参数调整。

##### 2.1.1.2 用户自定义"入睡所需时间"参数（默认10分钟）

"入睡所需时间"参数（`fallAsleepDelay`）是连接**意图表达**与**睡眠开始**的关键桥梁，其准确性直接影响周期计算可靠性。该参数定义为从点击按钮到实际进入睡眠状态的平均间隔，单位为分钟，**默认值10分钟**，可调范围**5-30分钟**，步进精度5分钟。

默认值10分钟的设定基于睡眠研究文献：健康成年人就寝后平均需要**10-20分钟入睡**（睡眠潜伏期），但个体差异显著。选择10分钟作为默认值，是在"不过度乐观"和"不过度保守"之间的平衡——对于入睡较快者，实际入睡略早于估算，唤醒时间稍有提前但仍在浅睡眠窗口内；对于入睡较慢者，实际入睡晚于估算，唤醒时间延后可能更接近预设时间。

参数设置界面采用**滑块配合分段标签**（5/10/15/20/25/30分钟），实时更新预览值。为辅助用户确定合适数值，应用提供引导性问题："您通常躺下后多久能睡着？"选项映射到建议值。更精细的校准通过历史数据反馈实现——如果用户频繁标记"不舒服"且实际醒来早于计划，系统提示"建议将入睡所需时间增加至15分钟"。

参数的动态调整场景需要特别考虑。用户的入睡时间可能因**日间疲劳程度、咖啡因摄入、睡前屏幕使用、环境噪音**等因素波动。应用不强制每晚调整，但在确认页显著位置提示"如果今晚感觉入睡会比平时慢/快，可以调整"，增强系统对个体状态变化的适应能力。

##### 2.1.1.3 实际入睡时间 = 点击时间 + 入睡所需时间

实际入睡时间的估算公式简洁明确：

```
estimatedFallAsleepTime = bedTimeClicked + fallAsleepDelay
```

这一计算在睡前确认页**即时完成并展示**，帮助用户验证参数合理性。展示格式为时间轴可视化："现在 23:30 → 入睡约需 10分钟 → 预计 23:40 入睡"，清晰呈现计算链条。

需要特别处理**跨午夜场景**：若用户23:55点击，入睡延迟10分钟，则估算入睡时间为次日00:05。日期字段以睡眠意图表达的日期为准（即"今晚"），确保逻辑一致性。另一边界情况是用户点击时间已过预设起床时间（如凌晨2点点击，预设7点起床）——此时即使最短延迟也无法完成完整周期，系统明确提示并预告兜底策略触发。

估算方法的固有误差需要诚实面对：实际入睡时间受多种因素影响，不可能精确预测；入睡定义本身也有模糊性（清醒到睡眠是渐进过渡）。然而，对于闹钟优化场景，这一误差是可容忍的——**睡眠周期计算的容错窗口（±10-15分钟）能够吸收大部分估算偏差**，且浅睡眠阶段本身具有20-30分钟的持续时间，为唤醒时机选择提供缓冲。

#### 2.1.2 最佳唤醒时间算法

##### 2.1.2.1 睡眠周期固定时长：90分钟（1.5小时）

**90分钟睡眠周期**是算法的核心参数，其科学依据和应用假设需要深入理解。这一数值源于睡眠科学家Nathaniel Kleitman和William Dement的开创性研究，他们发现成年人睡眠呈现规律的周期性波动，每个周期约90分钟，由NREM（包括浅睡眠N1/N2和深睡眠N3）和REM睡眠组成。这一"基础休息-活动周期"（BRAC）不仅存在于睡眠中，也体现在清醒时的警觉性波动中。

将90分钟作为**固定参数**是 deliberate 的设计选择。实际研究表明，个体周期时长存在显著差异（80-120分钟），且随年龄、睡眠剥夺程度、酒精摄入等因素波动。允许用户调整周期时长将引入认知负担（大多数用户缺乏自我评估能力），且误调可能导致系统性偏差。初始版本保持固定参数以简化设计，未来版本可基于长期舒适度反馈**推断个性化最优周期时长**。

##### 2.1.2.2 目标：预设起床时间前的最后一个完整周期结束点

算法目标的精确表述为：在满足**"不超过预设起床时间"**约束的前提下，找到从估算入睡时间开始、以90分钟为步长的**最大周期数**，该周期数的结束时刻即为最佳唤醒时间。这一目标设定基于两个核心假设：**完整周期优于不完整周期**（完成周期后唤醒更可能处于浅睡眠），**较晚的完整周期优于较早的**（在约束范围内最大化睡眠时长）。

具体示例：估算入睡时间23:40，预设起床时间7:00，可用时长7小时20分钟（440分钟）。完整周期数 = **floor(440/90) = 4**，最佳唤醒时间 = 23:40 + 6小时 = **5:40**。此时距离预设时间还有80分钟，用户损失这部分睡眠，但换取在第4周期末段（浅睡眠）唤醒的舒适度。

这一策略的**权衡本质**需要向用户透明传达。应用不隐瞒"提前唤醒"的设计，而是在确认页清晰展示"比预设时间早80分钟"，并解释"完成4个完整周期，在浅睡眠阶段轻柔唤醒"。用户若认为损失过大，可选择调整就寝时间或接受兜底策略。

##### 2.1.2.3 计算公式：最佳唤醒时间 = 估算入睡时间 + n×90分钟（n为最大整数且结果≤预设起床时间）

完整算法实现包含边界条件处理：

```swift
func calculateOptimalWakeTime(
    bedTimeClicked: Date,
    fallAsleepDelay: TimeInterval,
    targetWakeTime: Date
) -> Date? {
    let estimatedFallAsleep = bedTimeClicked.addingTimeInterval(fallAsleepDelay)
    let cycleDuration: TimeInterval = 5400 // 90分钟 = 5400秒
    
    let timeUntilTarget = targetWakeTime.timeIntervalSince(estimatedFallAsleep)
    
    // 边界条件：不足一个完整周期
    guard timeUntilTarget >= cycleDuration else {
        return nil // 触发兜底策略
    }
    
    let completedCycles = Int(floor(timeUntilTarget / cycleDuration))
    let optimalWakeTime = estimatedFallAsleep.addingTimeInterval(
        TimeInterval(completedCycles) * cycleDuration
    )
    
    // 精度保护：确保不超过目标时间
    return min(optimalWakeTime, targetWakeTime)
}
```

算法返回`nil`表示无法完成完整周期，此时系统激活兜底策略。这一设计确保各种输入组合下都有明确、合理的行为。

#### 2.1.3 浅睡眠阶段定位

##### 2.1.3.1 基于周期末段理论假设（周期最后20-30分钟为浅睡眠）

本应用对"浅睡眠阶段"的定位**完全基于理论假设**，而非实时监测。睡眠结构研究显示，典型90分钟周期中：初期以浅睡眠N1过渡，中段进入深睡眠N3，末段深睡眠减少，REM睡眠出现，最后回到N2浅睡眠完成周期。因此，**周期结束时刻前后大概率处于N2浅睡眠或REM睡眠阶段**，这两种状态都比N3深睡眠更容易唤醒。

这一假设的准确性存在**个体差异和情境波动**：年龄、睡眠剥夺、酒精、昼夜节律相位等因素都会影响周期结构。应用通过**舒适度反馈机制**在长期数据中识别模式——如果用户频繁标记特定窗口内的唤醒为"不舒服"，系统提示调整参数。

##### 2.1.3.2 唤醒窗口：最佳唤醒时间±10分钟可调

**唤醒窗口机制**将理论假设转化为可配置的闹钟触发区间。默认宽度**±10分钟**（总宽度20分钟），可调范围**±5至±30分钟**。窗口设计权衡多个目标：足够宽以覆盖理论误差，足够窄以避免过早唤醒损失，足够灵活以适应个体偏好。

窗口的技术实现涉及iOS本地通知调度。简化策略：在窗口起始时刻调度通知，若用户未响应，在窗口结束时刻调度第二个通知作为保底。更精细的实现可借助`BGTaskScheduler`，但会增加复杂度和审核风险。

### 2.2 兜底闹钟策略系统

#### 2.2.1 触发条件判定

| 触发条件 | 判定逻辑 | 典型场景 |
|:---|:---|:---|
| **条件一：周期不足** | `targetWakeTime - estimatedFallAsleepTime < 90分钟` | 入睡过晚、临时早起、午睡场景 |
| **条件二：时间过期** | `optimalWakeTime <= currentTime` | 操作延迟、夜间醒来查看应用 |

**条件一**是主要触发场景。例如用户凌晨1:30点击"我要睡了"，预设7:00起床，间隔仅5.5小时，无法完成完整周期。系统在确认页以**橙色警告**提示"剩余时间不足完整周期，将使用兜底策略"，展示具体兜底时间。

**条件二**涉及时间动态性。应用在用户完成确认流程后立即执行计算并与当前时间比较，若`optimalWakeTime <= now`，提示"最佳唤醒时间已过"并展示兜底方案。用户可选择接受、调整起床时间或取消记录。

#### 2.2.2 兜底方案选项

##### 2.2.2.1 方案A：用户自定义"最晚响铃时间"

方案A允许设置**独立于预设起床时间的最晚响铃时间**（`latestAlarmTime`）。典型用例：工作日7:00必须出门，但周末可接受7:30唤醒以换取更多睡眠。最晚时间通常设为预设时间之后（+15-30分钟），但也可设为之前作为绝对底线。

参数配置在设置界面完成，与预设起床时间并列显示。验证约束：`latestAlarmTime >= targetWakeTime - 90分钟`（否则与正常周期唤醒无区别），`latestAlarmTime <= targetWakeTime + 60分钟`（防止极端设置）。验证失败时提供明确错误提示和合理建议。

##### 2.2.2.2 方案B：严格在预设起床时间响铃

方案B是**最保守的兜底策略**，无论周期计算结果如何，始终在预设时间触发闹钟。适用于时间约束极高、不愿承担提前唤醒风险的用户，或对睡眠周期理论持怀疑态度者。

方案B可作为**新用户默认设置**，降低学习成本和尝试门槛。随着用户理解和信任建立，逐步引导尝试智能唤醒功能。

##### 2.2.2.3 方案优先级设置界面

兜底方案通过**分段控制器**在设置界面选择，选项清晰标注：

| 选项 | 显示名称 | 说明文字 |
|:---|:---|:---|
| 智能优先 | "智能优化（可能提前唤醒）" | "优先在浅睡眠阶段唤醒，可能早于预设时间" |
| 最晚兜底 | "最晚时间兜底" | "智能优化失败时，确保不晚于指定时间" |
| 严格按时 | "严格按时响铃" | "始终在预设时间响铃，放弃周期优化" |

选择方案A时动态展开时间选择器，选择方案B时隐藏关联控件。设置变更即时生效，已调度闹钟不受影响。

### 2.3 闹钟交互与控制

#### 2.3.1 响铃界面

##### 2.3.1.1 当前时间大字体显示

响铃界面采用**全屏沉浸设计**，当前时间以**超大字体（不小于72pt）**居中显示，确保半清醒状态下立即识别。背景采用**动态渐变**——从顶部深蓝紫色（夜间主题）向底部橙黄色（黎明主题）过渡，视觉上暗示"从睡眠到清醒"的状态转换。渐变色调根据实际响铃时间与预设时间的关系动态调整：智能唤醒偏冷色调，接近预设时间偏暖色调，提供 subtle 的时间紧迫感提示。

##### 2.3.1.2 闹钟标签/名称

时间下方显示**唤醒状态标签**，以 pill 形状徽章呈现：

| 标签类型 | 显示文字 | 背景色 | 说明 |
|:---|:---|:---|:---|
| 智能唤醒 | "✓ 浅睡眠优化唤醒" | 系统绿色（#34C759） | 周期计算成功触发 |
| 兜底闹钟 | "⏰ 兜底闹钟" | 系统橙色（#FF9500） | 兜底策略触发 |
| 延迟闹钟 | "延迟闹钟" | 系统蓝色 | 延迟后再次响铃 |

标签下方附加简短说明，如"您在浅睡眠阶段，现在醒来感觉最舒适"或"确保您不会迟到"，强化价值主张和情境理解。

##### 2.3.1.3 "停止"按钮（结束闹钟，记录实际醒来时间）

"停止"按钮占据屏幕底部**主要区域**（宽度60%以上，高度80pt），**绿色填充背景**，白色粗体文字"停止闹钟"。点击后立即：停止音频和振动，取消待处理通知，将当前时间写入`actualWakeTime`，触发舒适度反馈弹窗。

**误触防护**：按钮放置在屏幕下半部分，与上半部分时间显示形成视觉区分；或采用"长按1秒确认"模式，增加停止操作的有意性。需要在易用性和防误触之间根据用户反馈迭代优化。

##### 2.3.1.4 "延迟"按钮（10分钟后再次响铃，记录延迟次数）

"延迟"按钮与停止按钮**并列或上下排列**，**橙色描边或填充背景**，文字"再睡10分钟"，副标题显示剩余延迟次数"（还可延迟N次）"。点击后：暂停当前闹钟，调度10分钟后新通知，`snoozeCount`递增。

#### 2.3.2 延迟机制

##### 2.3.2.1 固定延迟时长：10分钟（用户不可自定义，简化设计）

**10分钟固定时长**是 deliberate 的简化决策。这一数值是广泛采用的"小睡"标准，用户有明确认知预期；过短（5分钟）不足以有效休息，过长（15-20分钟）可能重新进入深睡眠。固定值消除选择负担，保持操作一致性。

##### 2.3.2.2 最大延迟次数限制（防止无限延迟）

**默认限制3次**（最多30分钟额外睡眠），可在设置中调整至1-5次。达到上限后，延迟按钮变为不可用状态或显示"必须起床了"，强制用户停止闹钟。界面提示温和但坚定："已经延迟3次了，新的一天开始啦！"

##### 2.3.2.3 延迟后的唤醒策略：直接响铃，不再计算周期

延迟后的唤醒**采用简化策略**——10分钟后直接响铃，不重新计算周期。理论依据：10分钟远小于90分钟周期，睡眠阶段不会显著变化；重新计算引入复杂性且结果差异不大。延迟闹钟标签为"延迟闹钟"，与主闹钟区分。

#### 2.3.3 舒适度反馈

##### 2.3.3.1 响铃后弹窗询问"这次醒来感觉如何？"

舒适度反馈弹窗在停止闹钟后**立即呈现**，采用底部滑入的模态卡片设计。标题"这次醒来感觉怎么样？"语气亲切友好。内容区域展示本次睡眠核心数据：总时长、完整周期数、实际与计划的唤醒时间差异，为用户评估提供参考。

##### 2.3.3.2 选项：舒适 / 不舒服 / 跳过

| 选项 | 图标 | 颜色 | 操作 |
|:---|:---|:---|:---|
| 舒适 | 😊 笑脸 | 绿色 | 记录`.comfortable`，关闭弹窗 |
| 不舒服 | 😣 疲惫脸 | 红色 | 记录`.uncomfortable`，可选展开原因多选 |
| 跳过 | ⏭️ 箭头 | 灰色 | 保持`nil`，关闭弹窗 |

选项采用**大按钮设计**（直径72pt以上），支持快速半清醒操作。三种选择均视为有效完成反馈流程，不强制评价。

##### 2.3.3.3 不舒服标记用于后续数据分析

"不舒服"标记是**识别问题模式和优化机会的关键信号**。系统分析其与多维度数据的关联：标记是否集中在特定入睡时间、特定唤醒时机偏差、高延迟使用频率后等。重复模式提示系统性问题，生成针对性建议。

**后续跟进机制**：标记后的下次应用启动，显示关怀提示"上次醒来感觉不太舒服，有什么我们可以帮您的吗？"，链接到睡眠建议或设置调整。频率控制避免过度打扰。

##### 3.2.2.1 基于睡眠时长的健康评分（参考7-9小时成人标准）

| 睡眠时长 | 评分区间 | 等级 | 说明 |
|:---|:---|:---|:---|
| < 6小时 | 40-59 | 不足 | 显著低于推荐标准，健康风险 |
| 6-7小时 | 60-69 | 偏短 | 略低于推荐，部分人群可接受 |
| **7-9小时** | **80-100** | **理想** | **成人推荐标准，满分区间** |
| 9-10小时 | 70-79 | 偏长 | 可能提示睡眠质量或其他问题 |
| > 10小时 | 50-69 | 过长 | 显著超出，建议关注 |

评分采用**非线性映射**，7-9小时区间内满分，偏离时快速下降，强调适度睡眠的重要性。

##### 3.2.2.2 作息规律性评估（入睡时间标准差）

| 标准差 | 等级 | 说明 |
|:---|:---|:---|
| < 30分钟 | 优秀 | 作息高度规律，昼夜节律稳定 |
| 30-60分钟 | 良好 | 基本规律，偶有波动 |
| 60-90分钟 | 一般 | 作息不稳定，建议关注 |
| > 90分钟 | 较差 | 严重不规律，需要干预 |

规律性评估基于最近30天`bedTimeClicked`的时间分量标准差，是睡眠健康的重要预测指标——研究表明，**规律作息的益处可能超过不规律的长睡眠**。

##### 3.2.2.3 周期性建议推送

建议生成规则示例：

| 触发条件 | 建议内容 | 推送时机 |
|:---|:---|:---|
| 连续3天睡眠时长<6小时 | "检测到您最近睡眠不足，今晚尝试提前30分钟准备入睡" | 次日傍晚 |
| 周末入睡时间比工作日晚>2小时 | "您的社交时差较明显，尝试周末保持相近作息" | 周日晚上 |

    let date: Date                  // 6.1.1.2 记录日期
    let bedTimeClicked: Date        // 6.1.1.3 "我要睡了"点击时间
    let estimatedFallAsleepTime: Date  // 6.1.1.4 估算入睡时间
    let targetWakeTime: Date        // 6.1.1.5 预设起床时间

    // 6.3 衍生计算属性

        return (sleepDuration / timeInBed) * 100
    }
}

### 8.2 关键算法伪代码

#### 8.2.1 最佳唤醒时间计算

```swift
func calculateOptimalWakeTime(
    bedTimeClicked: Date,
    fallAsleepDelay: TimeInterval,
    targetWakeTime: Date
) -> Date? {
    let estimatedFallAsleep = bedTimeClicked.addingTimeInterval(fallAsleepDelay)
    let cycleDuration: TimeInterval = 5400 // 90分钟
    
    let timeUntilTarget = targetWakeTime.timeIntervalSince(estimatedFallAsleep)
    
    // 边界：不足一个完整周期
    guard timeUntilTarget >= cycleDuration else {
        return nil
    }
    
    let completedCycles = Int(floor(timeUntilTarget / cycleDuration))
    var optimalWakeTime = estimatedFallAsleep.addingTimeInterval(
        TimeInterval(completedCycles) * cycleDuration
    )
    
    // 精度保护
    optimalWakeTime = min(optimalWakeTime, targetWakeTime)
    
    return optimalWakeTime
}
```

#### 8.2.2 兜底策略决策

```swift
func determineAlarmTime(
    optimalWakeTime: Date?,
    targetWakeTime: Date,
    fallbackStrategy: FallbackStrategy,
    latestAlarmTime: Date? = nil
) -> Date {
    // 智能唤醒可行
    if let optimal = optimalWakeTime {
        return optimal
    }
    
    // 触发兜底
    switch fallbackStrategy {
    case .latestTime:
        return min(latestAlarmTime ?? targetWakeTime, targetWakeTime)
    case .strictTarget, .smart: // smart失败时回退到strict
        return targetWakeTime
    }
}
```
